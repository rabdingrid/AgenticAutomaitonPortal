# Deployment Portal — MVP Prototype

A working full-stack prototype for the deployment automation portal:
structured request form → task with multiple jobs → orchestrator
sequencing → history dashboard.

This replaces the email-parsing approach with explicit form input,
removing the guesswork (and missed details) that come with regex-parsing
free-text emails.

```
deployment-portal/
├── backend/              FastAPI + JSON-file "database"
│   ├── main.py            API endpoints
│   ├── db.py               All data logic (swap for real DB later)
│   ├── requirements.txt
│   └── db.json             Created automatically on first run
└── frontend/              React (Vite)
    ├── src/
    │   ├── App.jsx          Sidebar + routing
    │   ├── api.js            Fetch wrapper for backend calls
    │   ├── styles.css        All styling (no CSS framework needed)
    │   └── pages/
    │       ├── NewRequest.jsx   The request creation form
    │       ├── TaskDetail.jsx   Task + job stepper view
    │       └── History.jsx      Stats + task list
    └── package.json
```

---

## 1. Run the backend

```bash
cd backend
pip install -r requirements.txt
uvicorn main:app --reload --host 0.0.0.0 --port 9002
```

Or use the helper script: `./run.sh` (defaults to port 9002).

Confirm it's up: open `http://localhost:9002/health` → should return `{"status":"ok"}`.

Interactive API docs (auto-generated by FastAPI): `http://localhost:9002/docs`

---

## 2. Run the frontend

In a second terminal:

```bash
cd frontend
npm install
npm run dev
```

Open `http://localhost:5173`

The Vite dev server proxies any request to `/api/*` straight to
`http://localhost:9002`, so the frontend never needs to know the
backend's real port in code — see `vite.config.js`.

---

## 3. See it working immediately

The fastest way to see a populated portal without manually filling forms:

1. Go to the **History** page
2. Click **"🌱 Seed demo data"** — creates 3 sample tasks (one running,
   one fully resolved, one blocked/failed)
3. Click any task row to open its detail view
4. Inside a task, click a running job row to expand it — you'll see
   Jenkins parameters, steps, and logs
5. Use the **"Simulate: mark done"** / **"Simulate: mark failed"**
   buttons to manually advance the orchestrator and watch the next
   job in the sequence auto-start

This simulate buttons exist because there's no real Jenkins wired up
yet — in production, a Jenkins webhook would call
`PATCH /jobs/{job_id}/status` automatically when a build finishes.

## 4. How the pieces map to your existing pipeline

| Portal concept | Old email pipeline equivalent |
|---|---|
| Task | One `intake_report` / `case_key` |
| Job | One `run_plan[]` step |
| Job's `fields` | What `parser.py` used to extract via regex — now typed by the user instead |
| `jenkins_params` per job | `jenkins_params.py` output — same shape, cleaner input |
| Orchestrator job ordering | `orchestration_plan.py`'s utilities → yaml → liquibase → microservice → portal sequence |
| Task status (running/blocked/done) | `human_view.py`'s `status: "ready"/"blocked"` |

Nothing about your Jenkins job names, parameter schemas, or agent
routing logic needs to change — only the *input* method changes, from
"parse free text and hope" to "user fills explicit fields."

## 5. What's mocked vs real

| Feature | Status |
|---|---|
| Form → Task → Jobs creation | **Real** — actually persists to `db.json` |
| Orchestrator sequencing | **Real** — DAG deps in `depends_on[]`; parallel branches when deps allow |
| Sequential job dispatch (job 1 done → job 2 auto-starts) | **Real** — graph-aware; multiple ready jobs can start together |
| Jenkins parameter building | **Real logic**, but values are illustrative — wire to your actual `jobs.yaml` / `jenkins_profiles.yaml` next |
| Actual Jenkins trigger | **Mocked** — the "Simulate" buttons stand in for a real webhook |
| Actual GitLab/GitSpace merge | **Not implemented** — same as your current Phase 2 backlog item |
| Database | **JSON file** (`db.json`) — swap `db.py` internals for Postgres/SQLite later; every function signature in `db.py` stays the same so nothing above it needs to change |
| Auth / login | **None** — `requested_by` is a free-text field for now |
| Live updates | **Polling every 3s** on the Task Detail page — swap for websockets/SSE later if needed |

## 6. Next steps to make this production-real

1. **Wire real Jenkins.** Replace the `/jobs/{job_id}/status` manual
   PATCH with an actual Jenkins webhook callback that posts build
   result back to this same endpoint.
2. **Swap `db.py` for a real database.** Every function
   (`create_task`, `get_task`, `update_job_status`, etc.) keeps its
   exact signature — only the internals change from JSON file I/O to
   SQL queries.
3. **Add auth.** `requested_by` should come from a logged-in session,
   not a free-text field.
4. **Confirm job type → Jenkins job mapping.** Right now `db.py`'s
   `_JENKINS_JOB_MAP` is a hardcoded dict mirroring your `jobs.yaml`.
   Point it at the real config file once job names are confirmed.
5. **Add the approval gate.** Right now tasks execute immediately on
   submission. Add a "pending approval" status before `running` if
   you want a human sign-off step, matching the approval gate design
   already discussed for the email pipeline.
6. **DAG orchestration engine.** `orchestrator.py` already stores
   `depends_on[]` per job and dispatches ready nodes. Later, plug in
   Temporal/Prefect for durable execution, retries, and email-reply
   resume signals without changing the Task/Job schema.
